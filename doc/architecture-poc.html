High-Level Design

1.1 System Architecture Overview

Pattern: single-purpose pipeline behind one Azure Function App — not microservices, not even a full modular monolith. The POC's only job is to answer "can the AI pipeline extract this correctly?" Every other requirement (auth, review UI, reconciliation) is deliberately out of scope. One Function App hosts HTTP-triggered functions executing a linear pipeline: validate → convert → detect balloons → extract fields → write Excel → return result. No orchestration engine, no message queue, no persistent application database.

External dependencies: Azure AI Document Intelligence, Azure OpenAI, Azure Blob Storage, Azure Table Storage. No load balancer, no API gateway, no CDN — a Consumption or Premium Function App is sufficient at POC traffic levels.

1.3 Data Flow — "Extract one drawing"

1

Upload

User POSTs a PDF/image to /api/drawings/extract with the function key.

2

Validate

Function checks file type and page count/DPI; rejects with 400 below threshold (mirrors FR-03).

3

Store & log

File written to raw-drawings/{jobId}/source.pdf; job row created in Table Storage, status=Processing.

4

Rasterize

Each page converted to a high-resolution PNG in-process.

5

Layout extraction

Each page sent to Document Intelligence (prebuilt-layout) — returns text lines, tables, and bounding boxes, giving every candidate balloon/dimension a page coordinate.

6

Structured extraction

DI output + page image sent to Azure OpenAI (GPT-4o, vision) with a JSON-schema tool call: identify every balloon and return nominal value, tolerance, GD&T, and confidence.

7

Reconcile counts

AI's balloon list is checked against DI's raw circle/ellipse shape count; mismatch is surfaced in the response, not blocked — this is the exact signal the POC exists to measure.

8

Write outputs

Result JSON written to extracted-json/; Excel workbook generated from the same JSON via the configured template into exports/.

9

Return

JSON result plus a short-lived SAS URL to the Excel file returned inline; job row updated to status=Complete.

1.4 Architectural Trade-offs

#DecisionChosen becauseSacrificed
1Single Function App, no microservicesFastest path to a testable pipeline; one deployable, trivial to iterate on prompts.Service isolation and the module boundaries the Full architecture needs — this code is expected to be rewritten, not grown.
2Blob + Table Storage, no databaseZero schema migrations, zero ops, matches single-user/single-job usage.Queryability, relational integrity, reconciliation workflow state.
3No reconciliation gate, no authIsolates the variable under test — extraction accuracy — from workflow/security concerns.The requirements doc's core guarantee (100% reconciliation before export) does not hold here — output must be labeled unverified.
4Synchronous request/response, no queueSimplest to test with Postman; one drawing at a time, one user.Resilience and throughput — does not survive to batch volumes (200 drawings/package in the Full NFRs).

Low-Level Design

2.1 Core Modules & Classes

ModuleResponsibility
UploadHandlerHTTP trigger entry point; validates content-type/size, generates jobId, writes source blob, creates job record.
DrawingPreprocessorConverts PDF pages to raster images at a controlled DPI; rejects pages below the quality floor.
BalloonDetectorCalls Document Intelligence layout, isolates enclosed/circled numeric tokens as balloon candidates.
ExtractionOrchestratorBuilds the Azure OpenAI request (image + DI text layer + JSON schema), invokes the model, validates the response.
ToleranceNormalizerPost-processes raw tolerance strings into a normalized shape regardless of source notation.
ExcelWriterMaps normalized field objects onto the configured template's column layout.
JobStoreThin wrapper over Table Storage for job status read/write.

2.2 Design Patterns

  • Pipeline pattern — the five processing stages are composed as an ordered list with a uniform execute(context) signature, so stages can be reordered/swapped without touching the HTTP trigger.
  • Strategy pattern — ExtractionOrchestrator takes an IExtractionStrategy; the POC ships one (vision-grounded), but the interface exists so alternatives can be A/B tested.
  • Retry with exponential backoff — wraps Document Intelligence and Azure OpenAI SDK calls for 429/503; 3 attempts, base 2s, jittered.
  • Adapter pattern — Azure SDK clients wrapped behind small interfaces purely so unit tests can substitute fakes.

2.3 Error Handling & Edge Cases

ConditionHandling
Unsupported file type / corrupt file400 with a specific reason; no job created.
Page below DPI/quality threshold422; identifies which page(s) failed and why.
Document Intelligence timeout/5xx after retriesJob marked ExtractionFailed; Function returns 502.
Azure OpenAI returns malformed JSONOne repair re-prompt; on second failure, balloon emitted with confidence=0 — never dropped.
Content filter trips on a drawing imageBalloon flagged blocked=true; rest of the page still processed.
Balloon count mismatch (shapes vs. AI)Not an error — surfaced as balloonCountMismatch in the response; this is exactly what the POC measures.
Execution time approaching plan limitPage count capped per request (default 10); 413 above that rather than a timeout.

API Specification

3.1 Interface Protocol

REST/HTTP over Azure Functions HTTP triggers. No GraphQL, gRPC, or WebSockets — a POC with one caller (a tester and Postman/a minimal upload page) has no client-diversity or subscription requirement that would justify anything beyond plain synchronous REST.

3.2 Endpoints

POST /api/drawings/extract — uploads and processes one drawing synchronously.

Auth: x-functions-key header (Function-level key) — not a production auth mechanism.

GET /api/drawings/{jobId} — re-fetches a previously computed result (Table Storage lookup; no re-processing). Same response shape; 404 if unknown or expired (§4.3 retention).

3.3 Authentication & Authorization

None beyond the Azure Functions key. There is exactly one implicit role (tester/operator). Explicitly flagged as a gap to close before any non-throwaway use — see the Full architecture's Entra ID model.

4

Data Specification

4.1 Storage Overview

No relational database in the POC.

StorePurpose
Blob container raw-drawingsOriginal uploaded files, keyed by {jobId}/source.pdf.
Blob container exportsGenerated .xlsx files, keyed by {jobId}/characteristics.xlsx.
Azure Table Storage jobsOne row per job: filename, status, drawing number/revision, balloon counts, avg confidence, timestamps, error reason.

4.2 Why Blob + Table instead of a database

A relational store buys queryability and integrity the POC doesn't need yet — no reconciliation state machine, no cross-drawing reporting, no concurrent writers. Table Storage gives a queryable job log at effectively zero operational cost; Blob Storage is the natural fit for the actual payloads, which don't belong in a database row regardless of architecture stage.

4.3 Caching & Lifecycle

Policy

Caching: none. Every call to Document Intelligence/Azure OpenAI is live — caching results would risk masking the non-determinism the POC is measuring.

Retention: Blob lifecycle policy deletes everything in raw-drawings and exports 30 days after last-modified — a safety default for throwaway infrastructure processing potentially proprietary drawings.

Teardown: the entire resource group is expected to be deleted once the extraction-accuracy question is answered.

What This POC Does Not Answer

Not validated by a successful spike

Multi-user concurrency, the reconciliation/sign-off workflow, authentication/authorization, batch throughput at production volume, cost-at-scale, export-control/data-residency handling, and Excel template configurability beyond one hard-coded layout. All addressed in the Full production architecture.
