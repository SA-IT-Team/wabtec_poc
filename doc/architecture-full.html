High-Level Design

1.1 System Architecture Overview

Pattern: event-driven microservices, split along a genuine operational fault line: AI-bound, bursty, latency-variable work (balloon detection, extraction) versus human-paced, steady, consistency-critical work (review, reconciliation, sign-off). Services communicate synchronously via REST (through Azure API Management) for anything a client waits on, and asynchronously via Azure Service Bus for the extraction pipeline.

Ingestion API

Upload, file validation, drawing/revision metadata, versioning

Extraction Worker

Balloon detection + field extraction (Document Intelligence + Azure OpenAI), runs off the queue

Reconciliation API

Review sessions, discrepancy logging, sign-off, segregation-of-duties enforcement

Export Service

Template-driven Excel generation, batch packaging

Audit & Notification

Immutable audit log, job-status push notifications

1.3 Data Flow — "Drawing from upload to signed-off export"

1

Upload

Analyst uploads via SPA → Front Door → APIM (JWT validated, Analyst role) → Ingestion API.

2

Validate & enqueue

Ingestion API validates quality (FR-03), extracts title-block metadata (FR-02), creates Drawing + DrawingRevision rows (status=Uploaded), stores the file, enqueues an extraction-jobs message.

3

Extract

Extraction Worker (KEDA-scaled on queue depth) runs balloon detection + field extraction, writes Balloon/ExtractedField rows with confidence scores. Status → Extracted; event published to drawing-events.

4

Notify

Audit Service records the event; Web PubSub pushes "ready for review" to any connected SPA session.

5

Analyst review

Side-by-side view (FR-21); low-confidence balloons pre-sorted first. Each action written through to Postgres, cached in Redis for the active session.

6

Independent reconciliation

Second reviewer (enforced ≠ analyst, FR-22) repeats the pass. Mismatches logged with both identities (FR-23); balloon stays Unresolved until explicitly resolved.

7

Sign-off

Once 100% reconciled (FR-24 gate), reviewer signs off (FR-26): one transaction flips status + writes SignOff, then the outbox pattern publishes DrawingSignedOff.

8

Export

Export Service resolves the template (FR-17), reads the locked record, generates the .xlsx, stores it. Export from a non-signed-off revision returns 409 (FR-18).

9

Audit

Every step 2–8 writes an append-only AuditEvent (actor, action, timestamp, before/after) — FR-27.

1.4 Architectural Trade-offs

#DecisionChosen becauseSacrificed
1Async (Service Bus) pipeline, not sync request/responseExtraction latency is inherently variable; a queue gives backpressure and per-drawing retry isolation for the 200-drawing batch NFR.Immediate response — client must poll/subscribe (Web PubSub) instead of getting a result inline.
2Microservices split on AI-bound vs. human-paced workExtraction Worker load is bursty and wants to scale to zero between batches; Reconciliation load is steady and human click-driven. Scaling them together wastes cost either direction.Operational simplicity — needs APIM, service-to-service auth, distributed tracing, shared schema-ownership discipline.
3Strong consistency (Postgres ACID) for reconciliation stateSign-off is the compliance-critical gate — two reviewers must never both sign off the same revision. Needs transactional guarantees, not eventual consistency.Some write-throughput ceiling under heavy concurrent review — acceptable since review is human-paced; PgBouncer mitigates if it becomes real.
4LLM-based extraction (Azure OpenAI) over deterministic parsingDimension/tolerance/GD&T notation varies too much for a hand-written parser to generalize across drawing standards and eras.Determinism/full explainability — mitigated, not eliminated, by per-field confidence scores and the mandatory human reconciliation gate.

Low-Level Design

2.1 Core Modules & Classes (by service)

Ingestion API — DrawingUploadController, FileValidator (FR-03), TitleBlockExtractor, RevisionManager (FR-04: new revision never overwrites a reconciled one), ExtractionJobPublisher (outbox-wrapped).

Extraction Worker — ExtractionOrchestrator, BalloonDetector, ToleranceNormalizer, GdtParser (carried forward from the POC, now unit-testable with injected clients), ConfidenceScorer (drives FR-14 review sort order), ExtractionCircuitBreaker.

Reconciliation API — ReviewSessionService, BalloonReviewHandler, DiscrepancyLogger (FR-23), SegregationOfDutiesGuard (FR-22, rejects with 403 when reviewer = analyst), SignOffService (validates the 100%-reconciled precondition inside the status-flip transaction).

Export Service — TemplateResolver (FR-17, per-program column mapping), ExcelGenerator, PackageBundler (FR-20).

Audit & Notification Service — AuditEventConsumer (FR-27), NotificationDispatcher (Web PubSub groups keyed by drawing revision).

2.2 Design Patterns

PatternWhereWhy
Saga / explicit state machineDrawingRevision.status: Uploaded → Extracted → UnderReview → Reconciled → SignedOff → Exported, plus ExtractionFailed/StaleEvery legal transition explicit and testable; illegal transitions rejected at the domain layer.
Outbox patternIngestion (job enqueue), Reconciliation (sign-off event)Guarantees a Postgres write and its Service Bus message are never inconsistent.
Circuit breakerExtraction Worker → Document Intelligence / Azure OpenAIFails fast after N failures rather than piling up retries; jobs fall back to manual entry instead of blocking the queue.
Retry, exponential backoff + jitterAll outbound Azure SDK callsStandard mitigation for 429/5xx throttling.
Strategy patternIExtractionStrategy (from POC)Vision-grounded vs. text-only vs. future custom-model, selected per drawing-quality tier.
Repository patternData access in every serviceIsolates Postgres specifics from domain logic; unit testing without a live DB.
CQRS-liteStatus/Dashboard API reads a denormalized model refreshed by drawing-eventsKeeps FR-28/FR-29 reporting from competing with the transactional review write path.
Idempotency keysPOST /drawings, POST /drawings/{id}/exportA retried upload/export request can't create a duplicate revision or export.

2.3 Error Handling & Edge Cases

ConditionHandling
Document Intelligence / Azure OpenAI outageCircuit breaker opens; job ExtractionFailed; drawing remains fully usable via manual entry — the human path never depends on the AI path being up.
Malformed/non-schema LLM outputOne repair re-prompt; second failure → confidence=0 + extractionError, never dropped.
Duplicate balloon numbersFlagged at write time; status cannot advance past Extracted until resolved (FR-08) — enforced by the state machine.
Concurrent sign-off attemptsOptimistic concurrency via rowVersion; second attempt gets 409.
Reviewer account = analyst accountSegregationOfDutiesGuard rejects 403 — checked server-side, never trusted from the client.
Revision superseded mid-reconciliationIn-progress session marked Stale (FR-04) rather than merged; reviewer redirected to the new revision.
Export before sign-offRejected at the domain layer with 409 and the open-balloon list (FR-18) — no UI-only gate.
Poison message in queueService Bus dead-letters after max delivery count; scheduled alert on non-empty DLQ.
Upload interrupted / corrupted fileServer-side checksum validation before enqueue; specific, actionable 422.

API Specification

3.1 Interface Protocols

REST over HTTPS, via Azure API Management, for everything the SPA calls directly. Chosen over GraphQL because client data needs are fixed and resource-shaped, not ad-hoc/composable. Chosen over gRPC for external endpoints because the client is a browser SPA and REST/JSON keeps tooling simple. Azure Service Bus (async messaging) for Ingestion → Extraction Worker and the drawing-events fan-out. Azure Web PubSub (WebSockets) for pushing status changes in real time, avoiding client polling.

3.2 Endpoint Definitions

POST /api/v1/drawings — uploads a new drawing (or batch) and starts async processing.

Auth: Bearer JWT, role Analyst or Manager.

Response 202 Accepted 
{
  "drawingRevisionId": "7c1a...-uuid",
  "drawingNumber": "DWG-10245",
  "revision": "C",
  "status": "Uploaded",
  "statusUrl": "/api/v1/drawings/7c1a...-uuid",
  "realtimeChannel": "wss://bdx.webpubsub.azure.com/client/hubs/drawing-status?group=7c1a..."
}

Status codes: 202 accepted · 400 malformed · 409 idempotency key reused with different payload · 422 quality below threshold · 413 too large.

POST /api/v1/drawings/{drawingRevisionId}/signoff — reviewer signs off a fully reconciled revision, locking it.

Auth: Bearer JWT, role Reviewer; must not equal the analyst who confirmed any balloon in this revision.

Response 200 OK 
{
  "drawingRevisionId": "7c1a...-uuid",
  "status": "SignedOff",
  "signedBy": "reviewer@satincorp.com",
  "signedAt": "2026-08-26T14:32:10Z",
  "rowVersion": 4
}
Response 409 Conflict — incomplete reconciliation 
{
  "error": "IncompleteReconciliation",
  "message": "12 of 47 balloons are not yet reconciled.",
  "openBalloonIds": ["b-0007", "b-0012", "..."]
}
Response 403 Forbidden — segregation of duties 
{
  "error": "SegregationOfDutiesViolation",
  "message": "Signer must differ from the analyst who confirmed one or more balloons on this revision."
}

Status codes: 200 signed off · 403 segregation-of-duties violation · 404 unknown revision · 409 incomplete reconciliation or concurrent sign-off.

Additional endpoints

GET /drawings/{id}, POST /drawings/{id}/balloons/{balloonId}/review, POST /drawings/{id}/export, GET /packages/{id}/status follow the same contract conventions and are enumerated in the OpenAPI spec generated from this document — omitted here per the "at least 2 primary endpoints" scope of this document.

3.3 Authentication & Authorization

  • Identity provider: Azure Entra ID. SPA authenticates via OAuth 2.0 Authorization Code + PKCE; service-to-service calls use managed identity + client-credentials — no shared secrets in app config, all resolved through Azure Key Vault.
  • MFA: enforced at the Entra ID Conditional Access layer, not application code.
  • Authorization: Entra ID App Roles (Analyst, Reviewer, Manager, Admin) as JWT claims; APIM validates the token at the edge, and each service independently re-checks role + business-rule authorization — defense in depth.
  • Scoping: every request is scoped to programId; Entra ID group membership maps to allowed programs, checked on every read/write.

4.2 Data Storage Choices

StoreUsed forJustification
Azure Database for PostgreSQL – Flexible ServerAll relational entities aboveACID transactions non-negotiable for the sign-off gate; mature row-level locking supports optimistic concurrency; rich SQL supports FR-28/FR-29 reporting without a separate analytics store at this scale.
Azure Blob StorageSource drawing files, generated Excel exportsLarge binary objects don't belong in Postgres rows; Hot/Cool/Archive tiering maps onto §4.3 lifecycle policy.
Azure Cache for RedisActive review-session draft state, APIM rate-limit countersKeeps the side-by-side UI responsive without hitting Postgres on every keystroke; TTL'd, never the system of record.
Azure Service Busextraction-jobs queue, drawing-events topicDurable, dead-letter-capable messaging for the async pipeline — not a data store, noted because it sits on the data path.

4.3 Caching & Lifecycle Strategy

Policy

Cache invalidation: Redis review-draft entries invalidated on explicit save (write-through to Postgres) and a 30-min inactivity TTL; dashboard read-model entries invalidated by the drawing-events consumer, not a timer.

Blob lifecycle: Hot while a revision is active (pre-SignedOff); Cool 90 days after sign-off; Archive at 1 year — exact periods are program-configurable, since AS9102/PPAP retention varies by customer contract.

Deletion: application-level delete is always soft; hard deletion is a separate, audited compliance workflow that removes content while preserving a tombstone AuditEvent.

Audit retention: AuditEvent rows are never deleted by the application; purge, if ever required, is a separately governed DBA process.

If the Open Questions Resolve Differently

  • Multi-tenant SaaS instead of single-tenant: Program becomes tenant-scoped with row-level security in Postgres; Entra ID app registration becomes multi-tenant/B2B; Blob containers gain a tenant prefix and per-tenant SAS scoping.
  • Azure Government required for ITAR-flagged programs: Document Intelligence and Azure OpenAI model/region availability narrows substantially — likely needs a hybrid design (Gov boundary for controlled programs, Commercial for the rest), worth a dedicated spike before committing.
  • Native CAD input in scope: adds a new Ingestion path (CAD parser service) upstream of the existing pipeline; does not change the Extraction Worker → Reconciliation → Export chain.
